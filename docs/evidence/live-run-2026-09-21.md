Measured against `https://apple.moshe-barami111.workers.dev` at `buildSha 82fcd58` (= HEAD),
signed in as the project's own E2E account, Roblox Studio deliberately NOT connected.

## What the owner saw, and what the product does now

His screenshot showed a run that answered:

> I reached the step limit for this run. Progress so far is saved — send another message
> to continue.

…and charged **17 Credits** for it. The prompt was one part: "Create a glowing neon blue
anchored part named BeaconTower, 4x30x4 studs, at position (10, 15, 10)". One part should
not cost sixteen steps. It cost sixteen because Studio was not connected, the agent kept
trying, and `runDeliveredSomething` counted the READS as delivery, so nothing refunded.

The same prompt, same project, same disconnected Studio, against the build deployed tonight:

```
POST /api/admin/agent-run/bfad1c53-… {"mode":"stone","productModel":"apple","effort":"high"}

user      2026-09-21T11:09:35.620Z
assistant 2026-09-21T11:09:47.040Z   toolTrace: 0 calls   credits: 5
```

**11.4 seconds. Zero tool calls. 5 credits instead of 17.** And the answer is the right one:

> Studio isn't connected, so I can't create the part directly — open the Apple plugin in
> Studio and connect (Dashboard → project → "Connect Studio") and I'll build and verify it
> live. Meanwhile, here's a paste-ready script that does exactly what you asked:
>
> ```lua
> local part = Instance.new("Part")
> part.Name = "BeaconTower"
> part.Size = Vector3.new(4, 30, 4)
> …
> ```

It names the blocker, names the fix, and hands over something the user can use in the
meantime. No step limit. No loop.

**It is charged, and that is correct.** The refund rule (`apps/worker/src/run-refund.ts`)
gives Credits back for a run that produced NOTHING THE USER CAN KEEP. This run produced a
working script in eleven seconds. Refunding it would be the rule misfiring, not working.

## The projects shelf, same session

The owner's other complaint — "the projects are huge white boxes, everything is static" —
does not reproduce on the deployed build. The shelf renders per-project generated wave art,
a search field, tag chips and an archived tab. Its data is on screen well under a second:

```
/api/me                                    558 ms   (start 580)
supabase /rest/v1/projects  …limit=20      325 ms   (start 581)
supabase /rest/v1/projects  …(full list)   322 ms   (start 580)
supabase /rest/v1/projects  …archived      322 ms   (start 580)
supabase /rest/v1/projects?select=tags     315 ms   (start 581)
```

Four queries at one table, and each is argued in a comment where it is written: the limit-20
one is the sidebar's, the archived one exists so the Archived tab can show a count without
being opened, and the tags one is unfiltered on purpose because deriving chips from the
filtered list leaves exactly one chip on screen. They run concurrently and finish together,
so the duplication costs bytes, not time. Left alone deliberately.
